# 設計と性能

## 言語の選択

「この言語なら常に一番速い」という保証はありません。同じアルゴリズムなら計算量のオーダーは変わらず、割り当て、数式の解析回数、描画、転送が実際の体感速度を左右します。TypeScriptは実行時にはJavaScriptとなり、V8のJIT最適化が効きます。純Pythonのオブジェクトを使う逐次ループはこの用途では一般に不利ですが、NumPyやネイティブ拡張を使えば話は変わります。

今回はC++と同じくネイティブコードにコンパイルでき、GCを必要としないRustを採用しました。速度だけを理由にメモリー安全性を手放す必要がなく、単一バイナリで配布できます。[Rust公式の性能説明](https://rust-lang.org/)

C++とPythonの実装は測定していません。以下は、このリポジトリーの旧TypeScript実装とRust実装の比較です。

## 2026-09-07の実測

同一PC。旧TSはWindows / Node 24、RustはDocker Linux / Rust 1.98 release。各5回ウォームアップ後30回の平均で、展開とタートル座標計算を測定しました。描画・通信・AI推論は含みません。OS、ランタイム、バックグラウンド処理が異なるため、厳密な言語間ベンチマークではありません。

| ケース        |     枝 | 旧TypeScript |    Rust | この測定の倍率 |
| ------------- | -----: | -----------: | ------: | -------------: |
| シラカバ6世代 |  2,732 |     13.04 ms | 2.05 ms |        約6.4倍 |
| 密な分岐7世代 | 16,384 |     14.84 ms | 2.82 ms |        約5.3倍 |

別の実行ではTSは17〜19ms程度となりました。数ms単位の測定は揺れるため、固定の性能保証として扱わないでください。

### 通信まで含めた軽量化

当初はRustで全頂点を作って転送しましたが、密な樹木で約37MBとなり通信・圧縮が支配的でした。通常表示は枝の配置行列・先細り比率だけを送る方式に変更しました。

| ケース        | 全頂点のバイナリ | 表示用のバイナリ | 表示用の受信・デコードまで（キャッシュなし） |
| ------------- | ---------------: | ---------------: | -------------------------------------------: |
| シラカバ6世代 |  6,350,272 bytes |    394,520 bytes |                                      約96 ms |
| 密な分岐7世代 | 36,963,484 bytes |  1,246,372 bytes |                                      約87 ms |

バイト数はHTTP展開後のサイズ（ヘッダーを含む）です。HTTPではgzipも使用します。最初のケースは接続初期化も含むため、ケース間の時間を単純に比較できません。この測定はGPU描画時間を含まず、UI全体が5〜6倍速いという意味ではありません。標準プリセットの画面上の更新は実機で数ms〜数十msでした。

色変更はフロントの直近データを再利用するので通信しません。キャッシュが空の場合でも、バックエンド側の形状キャッシュを利用できます。

再測定：

```sh
docker compose up -d --build
npm install
node scripts/benchmark.mjs
docker build --target benchmark --progress plain -t komorebi-benchmark .
```

Dockerのベンチマーク層がキャッシュ済みの場合は `--no-cache-filter benchmark` を付けて再実行します。

## 処理の流れ

1. UIは入力を検証し、180msの間引き後にパラメーターを送ります。変更が続く場合は前のリクエストを中断し、古い結果を反映しません。
2. RustはASCIIコマンドの解析、上限付きの文字列展開、独立したシードによるタートル処理を行います。
3. 枝は16要素の行列、2要素の形状情報、太さ1要素。葉・花・つぼみは行列と太さだけをバイナリ送信します。
4. Three.jsは受信バッファーを直接インスタンス属性に設定します。枝の先細りと風はGPUの頂点シェーダーで描画します。影にも同じ変形を適用します。
5. GLB書き出し時だけ、Rustで通常の頂点・法線・UV・インデックスを生成します。表示用の先細りを通常メッシュへ焼き込むため、他の3Dソフトでも同じ形を再現できます。

Rustのf64計算は旧TSの座標・回転と誤差1e-9以内で比較済み。表示用のFloat32行列から再構成した頂点と、書き出し用の頂点は誤差2e-5以内で比較しています。旧TS実装とフィクスチャは比較用としてのみ保持し、配信コードには入りません。

## 上限とメモリー

- 展開25万文字、枝2万本、器官3万個、分岐深度512、座標の絶対値10万。
- API本文は128KiB。AIの指示は1,500文字。コードの評価・実行はしません。
- CPU計算は同時2件まで。Tokioのブロッキング専用処理に移し、接続・ヘルスチェックを止めません。
- AIは同時1件まで、タイムアウト付き。不正な出力は1回だけ修正を試します。
- 形状キャッシュは最大4件かつ64MiB。大きな書き出しデータは古いものから追い出します。これはキャッシュの上限であり、プロセス全体のメモリー上限ではありません。
- 世代上限の計算は0世代から何度も展開し直さず、前世代からの1回の走査で進めます。
- 3D表示にはブラウザー側のWebGL 2とGPUメモリーが必要です。GLB書き出しは大きな樹木ほど一時メモリーと時間が増えます。

## API

| API                       | 用途                                                        |
| ------------------------- | ----------------------------------------------------------- |
| GET `/api/health`         | Rustの稼働とバイナリプロトコルのバージョン                  |
| POST `/api/tree/generate` | PlantParams → 軽量表示用バイナリ                            |
| POST `/api/tree/export`   | PlantParams → 書き出し用バイナリ                            |
| GET `/api/ai/status`      | 指定したOllamaモデルの有無                                  |
| POST `/api/ai/generate`   | `{prompt, current?}` → `{name, description, model, params}` |

計算APIのバイナリは `KMR2` + uint32LEのJSONヘッダー長 + 4バイト境界のJSON + Float32LE / Uint32LE配列です。`web/src/geometry-client.ts` が境界・サイズ・バージョンを検証します。

AI生成は先行する空白を含むJSONストリームとして返します。接続切断時にOllamaへのリクエストを破棄するためです。開始前の入力エラー・競合はHTTP 4xx、開始後の推論エラーはHTTP 200のJSON内に `{error, code}` を返します。API利用者はHTTPステータスとJSONのerrorの両方を確認してください。

接続先・モデル名はサーバーの環境変数で設定し、ブラウザーから変更できません。既存Ollamaを標準として使い、Docker同梱GPU構成は明示的な選択肢です。公開サービス用の認証は実装していません。
